# Review Rationale Index (`RH#N`)

> **Why this file exists.** Five rounds of external spec review (2026-10-09) reshaped the
> catalog, generation and isolation design. **Every finding was reconciled into
> `REQUIREMENTS.md` / `PLAN.md`** (spec v8.0) — the original review files were deleted after
> reconciliation, so this is the surviving record of *why* the subtler rules read the way they do.
> Git history has the full rounds (`git log --diff-filter=D --name-only -- "*Review Feedback*"`).
>
> `PLAN.md` and `REQUIREMENTS.md` cite these entries as `RH#N`. **The spec is authoritative** —
> this file explains, it does not decide.

| ID | Rule | Why it reads that way |
|---|---|---|
| **RH#1** | A benefit has a **stable identity** (`benefits`) separate from its effective-dated versions (`benefit_catalog_versions`); instances point at the identity, not a version | A version change — even a typo fix — must never create a second entitlement for a period already generated. Frequency is part of the identity: a Quarterly→Monthly change **forks a new benefit**, because periods are keyed by frequency and a Quarterly and a Monthly period can share a start date. Only the curation judgment of "correction vs. new version" cannot be a constraint — it is a human call. |
| **RH#2** | `NULLS NOT DISTINCT` on the instance uniqueness constraint | Exactly one of `benefit_id` / `override_id` is always NULL, and Postgres treats NULLs as distinct by default — so the constraint meant to make generation idempotent **never fired**. |
| **RH#3** | A period uses the **earliest version whose window overlaps it**, and only once that version has actually started (`effective_from <= today`) | Picking the version at the period start silently drops a benefit the bank adds mid-period; generating before a future-dated version starts shows it as "Withdrawn — bank dropped this". An in-place correction shows **immediately** (it is an UPDATE of the same version row); only a genuine new version waits for the next period. |
| **RH#4** | The withdrawal sweep is **one stateless eligibility rule**, recomputed every time, in the same transaction as generation; scope is instances with `period_end >= today` | Separate one-way triggers left combinations undefined (dropped *and* suppressed, in any order). A past period's still-`Not Ordered` instance is **Lapsed** — "you missed this", not "the bank dropped it" — so the sweep must not touch it. Ordered/received/redeemed instances are never touched either. |
| **RH#5** | One definition of **"today"** (`Asia/Kolkata`, computed in the app) and of **"active on date D"** (`effective_from <= D AND (effective_to IS NULL OR effective_to >= D)`) | Vercel and Supabase both run in UTC — between midnight and 05:30 IST "today" is still yesterday, so a new quarter would appear 5.5 h late and a card's start date would land a day early. A future-dated version has `effective_to IS NULL` but is **not yet active**. |
| **RH#6** | A view generates the period's **full implied set** (period + elapsed months + half + year; a year/half view also generates everything nested inside it), bounded by `period_end >= cards.tracking_from` and `period_start <= today` | Generation must run on **every** view, or a mid-period addition never appears. `tracking_from` is tested against `period_end`, not `period_start`, so a card added in February still gets that year's annual benefit. A year view that generated only annual instances would leave quarters and months under-generated. |
| **RH#7** | Tenant isolation = composite foreign keys `(workspace_id, id)` on every per-workspace table + one query-scoping helper + a tenant-isolation test per server action **including reads** + PostgREST lockdown via a non-exposed `app` schema | RLS does not protect the app's own pooled connection and table owners bypass it, so isolation rests on app-layer scoping — which composite FKs make the **database** enforce rather than a habit. `REVOKE ALL` alone does not cover tables created by later migrations. Read tests matter more than write tests: reveal-code decrypts money. |
| **RH#8** | Identity keyed on the Supabase auth **user id**, never email; **no** FK to `auth.users`; signup **invite-only** via Supabase's built-in invite-by-email; sign-in moved into Phase 1 | Emails change, and email + Google sign-in can yield two identities for one address. A FK to `auth.users` exists only on a real Supabase project and would make every migration fail on plain local Postgres. A custom invite-code table brings a redemption race and a no-membership lockout; Supabase's built-in flow has neither. Tenant scoping is untestable without an authenticated session. |
| **RH#9** | Per-card `add` / `suppress` overrides, on/off for v1; `curation_status` (`uncurated` / `curated` / `no_benefits`) on `bank_card_types` | Users must be able to correct the shared catalog for their own card without affecting anyone else, and "this card genuinely gets nothing" must never look like "nobody has entered this card yet". |
| **RH#10** | Excel seeding: one `bank_card_types` row per **product** (not per physical card); catalog dedup key includes frequency; NULL frequency inherits from sibling rows; `instance_count` = the **most common** row count per (card, quarter); quarter-grained Monthly rows are skipped at import; version `effective_from`/`effective_to` derived from the quarters the benefit actually appears in | The sheet drifts, so **no count is hard-coded** — recompute at seed time. A flat NULL→Quarterly default forks fake identities for genuinely Annual/Monthly benefits. Taking the max count tripled the sheet's one Monthly benefit. Importing a quarter-grained Monthly row collides with live generation's per-month instance on the same `(card, benefit, period_start, instance_number)` key. Deriving dates from the CY column would make every version active all year. |
| **RH#11** | Reminders deferred to a later phase (the `notification_preferences` / `reminder_log` tables exist, unwired) | v1 scope. Now planned and scheduled in [`docs/backlog.md`](backlog.md) area A. |
| **RH#12** | Public-launch groundwork: privacy notice, account/workspace deletion with defined cascades, rate limiting; encrypted backups stored apart from the encryption key | Required before signup opens beyond invites, not before v1's invite-only launch. A backup holding every tenant's encrypted codes is only as safe as the key that decrypts them all at once. |
| **RH#13** | `Sold` is a `Coupon Redeemed` variant with `sold_for` set, not a schema status | Matches how the sheet is actually used. A sold instance is excluded from attention lists even while its status still reads `Coupon Received`. |
| **RH#14** | Terminology and doc consistency: calendar quarters and calendar years; "order" vs "use" (never "redeem"); no manual "Open Quarter" action; one auth user maps to one workspace; AES-GCM associated data = the row's own id | Avoids the ambiguity between ordering a benefit and using the coupon, while keeping the spreadsheet's own labels intact. Binding the ciphertext to its row stops an encrypted code being copied onto a different instance and still decrypting. |
| **RH#16** | A portal refusal — the RuPay portal or the bank refusing an order outright (benefit not available for this card, the card's limit used up, already ordered) — is recorded in **its own columns** on the benefit instance, not as a new `order_status` value; the instance's workflow status is left alone, and the refusal is excluded from automatic ordering for that period | A refusal is a fact about the **portal's view of the entitlement**, not a stage of the order — so folding it into `order_status` would have had to lie about the order's progress. The old workaround did exactly that: a card whose limit was already used was marked `Coupon Received`, which claims a coupon exists when none ever arrives, and buried the reason in a free-text `comments` field that the user can overwrite with their own notes on the next save. `order_status` also has a fixed vocabulary that the dashboard, the value totals, the withdrawal sweep and the queue all switch on; a status meaning "the portal said no" would have to be special-cased in all of them, and would still be the wrong shape — a refusal is scoped to a *period* and a *card*, while `order_status` is a single axis. As separate columns it composes with the workflow status instead of competing with it: the instance stays `Not Ordered` (it genuinely was never ordered), the refusal explains why, and the instance is excluded from automatic ordering so the worker does not retry it every hour. The user can dismiss the refusal to have it tried again. |
| **RH#15** | The deployed worker is a **Cloud Run Job swept hourly**, not a persistent daemon; it logs in fresh on every execution and keeps no browser profile or session state between runs; the event-loop daemon is retained as a local tool only | The 24-hour portal limit is enforced in the **database** (`portal_accounts.cooldown_until`), so eligibility is *computed*, not *awaited* — a scheduled sweep finds nothing to do for an account that is still cooling down, and therefore cannot over-order. Waking exactly at an unlock instant only matters if an order must land within minutes of the window opening, and a benefit's ordering window is days long. The daemon's other apparent advantage is illusory: the portal's `jwt` cookie expires **one hour** after login, so a daemon that sleeps for hours has a cold session anyway and must solve the CAPTCHA on every run, exactly like the batch job — a persisted profile cannot outlive the gap between runs. A job is also the cheaper and more observable shape (billed per execution, self-limiting, one log entry per run) where a daemon is an always-on bill. Fresh login per run additionally satisfies the existing rule that a job must not persist `storageState`, cookies, JWTs, or session IDs. |
